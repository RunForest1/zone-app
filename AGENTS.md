# zone-app

Стелzone: каталог предметов игры Stalzone: список с фильтрами и детальная страница
предмета с историей продаж и текущим аукционом.

## Стек

- Next.js 16 (App Router) + React 19
- TypeScript
- Tailwind CSS 4
- Turbopack + React Compiler
- PostgreSQL + Prisma (постоянное хранилище истории сделок)
- Docker Compose (db, migrate, web, worker, **bot**)
- Данные — локальная база `src/lib/stalzone-database-main/ru` (json-файлы)
- Аукцион — внешний API `https://eapi.stalzone.com` (см. «API аукциона»)
- Telegram-уведомления — **grammY**, трафик до `api.telegram.org` идёт через
  общий прокси-стек `shared-proxy` (Xray-core, живёт вне этого
  репозитория — см. «Телеграм-бот уведомлений»); прокси **http** (порт 1081),
  потому что fetch Bun не умеет socks.

## Команды

```
bun dev      # сервер разработки
bun build    # production-сборка
bun start    # запуск production-сборки
bun worker   # фоновый воркер синхронизации истории
bun bot      # телеграм-бот уведомлений
bun migrate  # применить миграции (prisma migrate deploy)
```

## Архитектура

### Данные (`src/lib/items`)

- `ItemsDatabase` (`index.ts`) — рекурсивно читает все json из `<root>/items`, собирает
  предметы в объект по id (поле `items`). Иконка предмета — `icons/<category>/<id>.png` (прописана в поле `icon` относительно корня базы, либо `null`, если файла нет).
  Варианты предметов (папки `_variants/<id>`) складываются в поле `variants`;
  чтение вариантов отключается опцией `includeVariants: false` (в приложении
  варианты не читаются — интерфейс строится на данных аукциона).
- `store.ts` — единый экземпляр базы (`itemsDatabase`). База читается один раз,
  **не создавайте новый `ItemsDatabase` на каждый запрос**.
- `catalog.ts` — `toSummary` (предмет → краткая версия для каталога), `applyFilters` (чистая функция фильтрации и сортировки), `topCategories` (верхние категории
  с числом предметов), справочники `CATEGORY_TREE`/`RANK_OPTIONS`/`RANK_COLORS`/`SORT_OPTIONS`,
  хелперы `categoryLabel`, `rankLabel`, `rankColor`, `itemName`, `iconUrl`.
  Русские названия категорий лежат здесь — при добавлении категорий правьте `CATEGORY_TREE`.
  Ранги сортируются от легендарного к низкому; «по рангу» — сортировка по умолчанию,
  «по разделам» использует порядок `CATEGORY_TREE`.

### API аукциона (`src/lib/auction`)

- `SZApi` — клиент `https://eapi.stalzone.com`. Читаются публичные данные (лоты,
  история), поэтому нужна авторизация «по секрету»: заголовки `Client-Id` и `Client-Secret` (см. <https://eapi.stalzone.com/auth.html>, «Secret Based
  Authentication»). Методы `getLots(item)` и `getHistorySince(item, since, maxPages)` типизированы
  (`AuctionLot`, `PricePoint`); ошибки — исключением.
- `getSzApi()` — берёт креды из переменных окружения `CLIENT_ID` и `CLIENT_SECRET` (`.env`; для секрета поддерживается и старое имя `SZ_API_TOKEN`). Если их нет,
  возвращает `null`, и блоки на странице показывают заглушку.
- `getLots` постранично добирает все активные лоты (страница — 200, ограничение 600);
  `getHistorySince` — сделки с момента `since` (пачки по 6 страниц), не больше
  `BACKFILL_PAGES` (200) при backfill и `INCREMENT_PAGES` (5) при докачке
  (её гоняем каждые 2 минуты, поэтому новых сделок за цикл мало).
- Параметры API: `limit` (макс. 200, по умолчанию 20), `offset`, `additional`;
  у лотов ещё `sort` и `order` (в клиенте не используются — сортировка в интерфейсе).
- `additional: true` (в клиенте включён) даёт дополнительные поля по лоту/сделке:
  `qlt` (качество), `ptn` (точка), `buyer` (покупатель), `it_transf_count` и др.
  Для истории доп. поля тянем только с первой страницы: если у предмета нет
  `qlt`/`ptn`, остальные страницы запрашиваются без них (меньше трафика).
- Формат ответа: лоты — `{ total, lots: [...] }`, история — `{ total, prices: [...] }`.

### Кэш данных аукциона (`src/lib/auction/data.ts`)

- `loadLots(itemId)` и `loadHistory(itemId, days, window)` — обёртки над `SZApi` с директивой `use cache`. Лоты живут ~1 минуту (`revalidate: 60`), история —
  ~5 минут (`revalidate: 300`), тег — `item:<id>` (для `revalidateTag`).
- Ключ истории включает `window` — время запроса, **округлённое вниз** до 5 минут
  (`windowOf`). Поэтому все фильтры (качество, точка) и соседние запросы попадают
  в один кэш-энтри: API дёргается не чаще раза в 5 минут на предмет+период,
  а смена фильтра — мгновенная (фильтрация уже готовых данных в памяти).
- `ItemHistory` и `ItemLots` — раздельные Suspense-блоки: лоты (один запрос)
  показываются раньше истории (у «горячих» предметов это десятки страниц).
- `loadHistory` **читает историю из PostgreSQL**, а не из API: страница в API
  не ходит. `loadLots` — как и раньше из API (лоты в БД не сохраняются).
- Историю пополняет синхронизация (`src/lib/sync.ts`): воркер по избранному и
  подтягивание по открытию карточки (`syncOnDemand`, не чаще `SYNC_ON_DEMAND_MIN_MS`).

### База данных и воркер

- Схема (`prisma/schema.prisma`): `TrackedItem` (предметы, по которым храним
  историю; поле `favorite` — избранное, его синкает воркер),
  `ItemSync` (состояние синхронизации: `backfilledAt`, `lastSyncedAt`,
  `lastSaleTime`, `lastError`), `Sale` (сделки: время, цена, количество,
  качество, точка и ключ дедупликации `key`), `SyncLog` (журнал прогонов),
  `AlertChat` и `AlertEvent` (подписки и лог уведомлений — см. «Телеграм-бот»).
- Миграции лежат в `prisma/migrations/` (начальные — сделки и индексы, затем
  подписки и события алертов); применяются командой `bun migrate`
  (`prisma migrate deploy`) или сервисом `migrate` в compose.
- `src/lib/db/index.ts` — Prisma-клиент как singleton (`globalThis` в dev).
- `src/lib/db/sales.ts` — сделки и избранное: `readSales`, `saveSales` (вставка
  пачками по 1000, дубликаты пропускаются), `latestSaleTime`, `freshSales`
  (только новые сделки — для алертов), `saleByKey`, `saleKeyOf` (ключ сделки —
  тот же, что `Sale.key`), `saleStats` (средняя без выбросов, медиана и число
  сделок по срезу качества и точки), `lastSalePrice`, `ensureItem`,
  `setFavorite` / `listFavoriteIds` / `isFavorite`.
- `src/lib/db/alerts.ts` — `listActiveAlertChats`, `upsertAlertChat`,
  `wasAlertSent` / `markAlertSent` (постановка в очередь), `listPendingAlertEvents` /
  `markAlertEventSent` (очередь для бота) — см. «Телеграм-бот».
- `src/app/actions.ts` — серверный экшен `toggleFavorite`: звёздочка в каталоге
  и на странице предмета переключает избранное.
- `src/lib/sync.ts` — общая синхронизация: `syncItem` (backfill при первом
  появлении предмета, дальше только новое; пишет `SyncLog`/`ItemSync`, ставит
  алерты) и `syncOnDemand` (подтягивание по открытию карточки, не чаще
  `SYNC_ON_DEMAND_MIN_MS`; строку предмета создаёт, но избранным не делает).
- `src/worker/index.ts` — воркер: раз в `WORKER_INTERVAL_MS` (по умолчанию
  **2 минуты** — избранных мало, поэтому обходим часто) синкает **только
  избранные** предметы (`TrackedItem.favorite`). Если выборка упёрлась в лимит
  страниц (`complete: false`), `backfilledAt` не ставится и `lastSaleTime` не
  сдвигается — backfill повторится на следующем прогоне (дубликаты отсекает
  `key`). Ошибки по предмету пишутся в `SyncLog` и `ItemSync.lastError` и не
  останавливают цикл; SIGTERM/SIGINT — корректное завершение.
  В конце каждого прогона воркер чистит старое: сделки и записи `SyncLog` старше
  `WORKER_RETENTION_DAYS` (35 дней; нужно максимум 30 + запас).
  Избранное задаётся вручную (звёздочка в вебе или `/track` в боте) и не
  снимается само; неизбранные предметы фоном не синкаются — их история
  подтягивается только при открытии карточки. Для алертов это значит:
  уведомления приходят по избранным предметам.
  После сохранения новых сделок по предмету воркер вызывает
  `checkAlerts(itemId, sales)` (см. «Телеграм-бот») — сама отправка сообщений
  в Telegram делается отдельным процессом `bot`, воркер только пишет событие
  в `AlertEvent`.
- `src/app/api/health/route.ts` — healthcheck: `SELECT 1` в БД (`await connection()`,
  чтобы роут не закэшировался на сборке).
- Переменные окружения: `DATABASE_URL`, `CLIENT_ID`, `CLIENT_SECRET`, `DOMAIN`,
  `WORKER_INTERVAL_MS` (по умолчанию 2 минуты), `WORKER_BACKFILL_DAYS`,
  `WORKER_RETENTION_DAYS`, `SYNC_ON_DEMAND_MIN_MS`, плюс переменные бота (см. ниже).
  `.env` в репозиторий не коммитится (он в `.gitignore`).
- Docker: `Dockerfile` — multi-stage с target-ами `web` (standalone) и `worker`
  (фоновые процессы на bun: синхронизация истории, телеграм-бот и разовый прогон
  миграций — один образ запускается с разной командой); `docker-compose.yml` — `db`
  (Postgres + именованный volume `db-data`), `migrate` (одноразовый, применяет миграции
  до старта), `web`, `worker`, `bot` (подключает внешнюю сеть `shared-proxy-net`);
  у сервисов `restart: unless-stopped` (кроме `migrate`), healthcheck и
  ротация логов (`json-file`, 10 МБ × 3). Запуск: `docker compose up -d --build`.

### Серверное и клиентское

- Нормы обновления аукциона: лоты — раз в минуту, история — раз в 5 минут
  (это и есть TTL кэша в `data.ts`). Документированных лимитов у API нет,
  поэтому наращивать частоту не надо — достаточно кэша.

- Каталог (`app/page.tsx`) — серверный компонент: собирает список предметов,
  передаёт краткие версии в клиентский `ItemCatalog`. Раскладка во всю ширину:
  слева меню категорий (`CategoryNav`), сверху поиск, фильтр по рангу и сортировка
  (по рангу / по разделам / А→Я / Я→А; по умолчанию — по рангу, от легендарного
  к низкому; «по разделам» недоступна внутри одной категории, «по рангу» —
  при выбранном конкретном ранге). Категории в меню —
  только верхний уровень; показываются те, что есть в данных. Карточки
  показываются порциями по 120 (кнопка «Показать ещё»), есть «Сбросить».
  У каждой карточки — звёздочка избранного; **избранные всегда идут первыми**
  (избранное читается из БД на каждый запрос, поэтому список в `<Suspense>`).

- Детальная страница (`app/items/[id]/page.tsx`) — серверный компонент,
  читает предмет по `id` (иначе `notFound()`), показывает иконку, категорию
  и ранг (окрашенный цветом ранга), а также звёздочку избранного. Характеристик на странице нет — только
  «История продаж» (`ItemHistory`) и «Текущий аукцион» (`ItemLots`), каждый
  в своём `<Suspense>`. Обращение к `params` обёрнуто в `<Suspense>` — иначе dev-валидация «мгновенной навигации» ругается
  (см. /docs/messages/instant-shell-url-data).

- `ItemHistory` (серверный) тянет лоты и историю за выбранный период, дальше работает
  клиентский `MarketHistory`: фильтры качества (`qlt`, названия и цвета из `@/lib/auction/quality`) и точки (`ptn`; отсутствующая точка считается нулём, поэтому в списке есть «0»), график цены (`PriceChart`). Таблица лотов («Текущий аукцион», `ItemLots`) живёт в `LotsTable`: страницы по 20 и сортировка кликом по заголовку.

- Статистика рынка: средняя цена (с числом сделок за период) и медиана — по **совершённым сделкам** за выбранный период (и с учётом фильтров качества/точки), последняя сделка — из истории, мин. предложение — минимальный выкуп активных лотов. Средняя считается **без выбросов** («вкиды»/переброс валюты): отбрасываются верхние `OUTLIER_TRIM` (5%) и цены выше `OUTLIER_MEDIAN_FACTOR` (5×) медианы (см. `cleanedPrices` в `@/lib/auction/market`); сколько отброшено — подписано под статистикой. Прибыль на странице = `(1 − комиссия) × средняя − мин. предложение`, маржа = прибыль / средняя × 100; ставка `MARKET_FEE` (5%) общая с алертами (`estimateProfit` в `@/lib/auction/market`). В алертах бота база другая — цена конкретной сделки (см. «Телеграм-бот»).

- Фильтры качества и точки показываются, только если признак есть в данных,
  но значения перечисляются полным диапазоном: заточка 0–15, качество 0–5
  (`featureRange` в `@/lib/auction/market`), чтобы варианты не «пропадали»,
  когда по какому-то значению пока не было сделок или лотов.

- Фильтры рынка — период (7/14/30 дней) и качество/точка — берутся из адреса
  (`?days=&qlt=&ptn=`): ссылки-«чипы» лежат в `MarketHistory`, разбор — `parsePeriod`/`parseFeature`, сборка адреса — `marketHref` (`@/lib/auction/period`).
  Клиентского состояния у фильтров нет, поэтому они работают и без гидратации,
  а данные выбираются и фильтруются на сервере.

- `ItemHistory` при открытии зовёт `syncOnDemand` (подтягивает историю с троттлингом `SYNC_ON_DEMAND_MIN_MS`) и вызывает `await connection()` (`next/server`) — только потом `Date.now()` — до `connection()` пререндер запрещает нестабильные значения;
  окно считается по календарным датам. История тянется страницами (по 200,
  пачками по 6, не больше 30 страниц) и агрегируется в `summarize` (`@/lib/auction/market`): ряд графика — ~120 интервалов со средней ценой,
  статистика (средняя, медиана, число сделок и штук, мин/макс, последняя) —
  по всем сделкам окна. Если лимита страниц не хватило на весь период,
  UI пишет «период покрыт не полностью». Дата/время форматируются детерминированно
  (`src/lib/format.ts`, Москва UTC+3) — иначе SSR и браузер дают разные строки
  и ломается гидратация.

- Иконки не лежат в `public`, их отдаёт route handler `app/icons/[...path]/route.ts` из папки базы.

### Внешний вид

Тёплая светлая тема. Палитра вынесена в токены в `globals.css` (`@theme`):
классы `bg-surface`, `text-accent` и т.п. Структура токенов повторяет lunar-zone.ru
(уровни поверхностей, границ и текста), оттенки — тёплые.

| Токен           | Цвет      | Назначение                                        |
| --------------- | --------- | ------------------------------------------------- |
| `background`    | `#FAF8F4` | фон страницы                                      |
| `surface`       | `#FFFFFF` | карточки и панели                                 |
| `surface-muted` | `#F4EEE6` | вложенные поверхности и ховер                     |
| `foreground`    | `#2B2621` | основной текст                                    |
| `muted`         | `#7C7268` | вторичный текст                                   |
| `faint`         | `#A89E92` | третичный текст и подписи                         |
| `line`          | `#EBE3D8` | границы                                           |
| `line-strong`   | `#DBD0C0` | границы заметнее                                  |
| `accent`        | `#B06A37` | акцент: ссылки, активные элементы, главные кнопки |
| `accent-soft`   | `#F8E9D7` | подложка акцента                                  |

Плюс тень `--shadow-card` (класс `shadow-card`). Блоки — белые панели `rounded-xl` с рамкой `line` и тенью `shadow-card`: шапка и подвал сайта,
меню разделов, панель фильтров, карточки и секции на странице предмета.

Ранги окрашены: цвета лежат в `RANK_COLORS` (`catalog.ts`), хелпер `rankColor`.
Рамка карточки, свечение (`box-shadow`) и подпись ранга красятся в цвет ранга;
у предметов без закреплённого ранга (`DEFAULT`) рамка и свечение серые
(ранг можно выбрать на странице).

## Телеграм-бот уведомлений (`src/bot`, `src/lib/alerts`)

Бот следит за **сделками**, которые воркер сохраняет в `Sale`, и шлёт в групповой чат
уведомление, когда сделка выглядит выгодной. Фильтры настраиваются командами и кнопками
прямо в Telegram.

Ключевое: **бот не источник правды по сделкам** — в `eapi.stalzone.com` он не ходит и
логику воркера не дублирует. События считает воркер, бот только отправляет то, что уже
посчитано, и читает БД.

### Экономика алерта

Площадка берёт **5% с продажи** (`MARKET_FEE` в `@/lib/auction/market` — та же ставка,
что и на сайте). Считаем, что покупаем по цене прошедшей сделки `P`, а продаём по средней
рынка `A` (того же предмета, того же качества и точки, за 7 дней, **без самой
этой сделки и без выбросов** — верхних 5% и цен выше 5× медианы):

```
прибыль = (1 − 0.05) × A − P
маржа   = прибыль / A × 100
```

Порог срабатывания: `прибыль ≥ minProfit` **и** `маржа ≥ minMargin` (если задан), пороги
включительные. Полезная связка: `маржа m%` ⇔ цена ниже средней на `5% + m` (например,
`margin 10` ⇒ цена минимум на 15% ниже средней).

**Лоты (мин. предложение) для алертов не используются** — за ними в API не ходим.

### Данные

- `AlertChat` — подписка чата: `minProfit` (BigInt, по умолчанию 50 000), `minMargin` (Float?),
  `categories`/`ranks`/`qualities`/`points` (наборы, пусто = без ограничения), `active`, `title`.
  Качество — `qlt` 0–5, точка — `ptn` 0–15 (отсутствующая точка = 0, отсутствующее качество
  под непустой набор качеств не подходит).
- `AlertEvent` — очередь и лог отправки: `profit`, `margin`, `lastPrice`, `stats`
  (JSON — массив `{ days, average, median, deals }` за 7/14/30) и `sentAt` (`null` = ещё
  в очереди). Дедуп — `@@unique([alertChatId, saleKey])`.

### Детектор (`src/lib/alerts`)

- `profit.ts` — чистая экономика: `ALERT_PERIODS` (7/14/30), `estimateFlip(price, average)`,
  типы `PeriodStats`/`FlipEstimate`. Ставка комиссии — общая `MARKET_FEE` из `@/lib/auction/market`.
- `detect.ts` — чистые фильтры: `matchFilters` (активность, качества, точки, разделы, ранги)
  и `matchThreshold` (пороги прибыли/маржи); `detectAlerts(deal, chats, estimate)` возвращает
  подходящие чаты.
- `index.ts` — `checkAlerts(itemId, sales)`: по каждой новой сделке считает рынок (7/14/30)
  по её срезу (качество + точка сделки), оценивает выгоду и пишет подходящие события
  в `AlertEvent`. В API не ходит, в Telegram не шлёт.

Вызывает её воркер — после `saveSales`, только по новым сделкам и только на инкрементальном
проходе (на backfill уведомления не шлём, иначе зальём чат историей за 30 дней).

### Процесс `bot` (`src/bot`)

- `index.ts` — создаёт `Bot`, при старте зовёт `getMe()` (падает сразу, если токен/прокси
  неверные) и `setMyCommands` (палитра команд). Раз в `BOT_POLL_MS` (10 с) забирает
  неотправленные `AlertEvent`, шлёт в чат (с кнопкой избранного) и ставит `sentAt`.
- `commands.ts` — команды: `/start`, `/chatid` (без ограничений) и админские `/menu`,
  `/status`, `/filter`, `/pause`, `/resume`, `/track <id>` и `/untrack <id>`
  (избранное по id из ссылки на предмет). Фильтры: `/filter minprofit 30000`,
  `/filter margin 10` (`off`), `/filter categories Оружие,Артефакты`,
  `/filter ranks Мастер,Легенда`, `/filter qlt 2-5` (`2,3,4,5`, `все`),
  `/filter ptn 0-15` (`все`).
- `menu.ts` — настройки кнопками (инлайн-клавиатура): пауза, пресеты прибыли/маржи,
  переключатели качества, точки, разделов и рангов; плюс кнопка «⭐ в избранное»
  под уведомлениями (`favoriteKeyboard`).
- `auth.ts` — `isAllowedUser` по `ALERT_ADMIN_USER_IDS` (**user.id**, не chat.id; пусто =
  менять настройки не может никто).
- `format.ts` — текст сообщения (HTML): имя-ссылка `${DOMAIN}/items/<id>`, ранг, цена сделки,
  последняя сделка, прибыль (после 5%) и маржа, качество/точка и рынок тремя строками
  (7/14/30: средняя · медиана · сделок).
- `proxy.ts` — прокси для Telegram. **Встроенный fetch Bun не умеет socks и не применяет
  node-агенты**, поэтому ходим через нативный параметр `proxy` к **http-inbound Xray
  (порт 1081)**: `TELEGRAM_PROXY_URL=http://shared-proxy:1081`.

### Дедуп

Три уровня: `freshSales` в воркере (старые сделки не считаются новыми),
`@@unique([alertChatId, saleKey])` в `AlertEvent` (повторная постановка невозможна) и `sentAt`
(повторная отправка невозможна).

### Переменные окружения (дополнение к `.env.example`)

```
TELEGRAM_BOT_TOKEN=              # токен от @BotFather
TELEGRAM_PROXY_URL=http://shared-proxy:1081
ALERT_ADMIN_USER_IDS=            # telegram user.id через запятую
BOT_POLL_MS=10000                # как часто бот проверяет очередь, мс
```

### Прокси `shared-proxy` (вне этого репозитория)

Xray-core с двумя inbound: socks `1080` и http `1081`. Поднимается **отдельным стеком**
(в репозитории его нет, на сервере лежит вне проекта) и создаёт сеть `shared-proxy-net`;
сервис `bot` подключается к ней как к `external` и обращается по **имени контейнера**
`shared-proxy`. Конфиг собирается из переменной `VLESS_URL` (ссылка-подписка) при старте
контейнера.

## Соглашения по коду

- Комментарии — на русском.
- Код простой и читаемый, пригодный для правок руками.
- Условия — в блоках с фигурными скобками, без однострочных `if (...) ...;`.
- Переиспользуемые куски выносим в `src/components` и `src/lib`.
- В `next.config.ts` включены `cacheComponents`, `partialPrefetching`, `reactCompiler`.
  При включённом `cacheComponents` не используются `dynamic`/`revalidate`/`fetchCache`,
  а несрочные данные оборачиваются в `<Suspense>` (см. `node_modules/next/dist/docs/`).
- Бот и воркер — отдельные процессы с разной зоной ответственности: воркер
  ничего не знает про Telegram, бот ничего не знает про `eapi.stalzone.com`.
  Общий код между ними — только чтение/запись через Prisma и чистые функции
  вроде `MARKET_FEE`/`estimateFlip`/`detect.ts`.
