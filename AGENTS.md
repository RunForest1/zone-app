# zone-app

Каталог предметов игры Stalzone: список с фильтрами и детальная страница предмета
(история продаж и текущий аукцион) плюс телеграм-бот, который периодически
сканирует **активные лоты** по избранным артефактам и присылает уведомления
о выгодных.

Концепция алертов — **снайпинг лотов**, а не охота за новыми сделками: свежие
сделки скупают боты, а лот, который висит заметно дешевле недавней средней
по своему качеству и точке, — реальная возможность.

## Стек

- Next.js 16 (App Router) + React 19
- TypeScript
- Tailwind CSS 4
- Turbopack + React Compiler
- PostgreSQL + Prisma (постоянное хранилище истории сделок)
- Docker Compose (db, migrate, web, worker, **bot**)
- Данные — локальная база `src/lib/stalzone-database-main/ru` (json-файлы)
- Аукцион — внешний API `https://eapi.stalzone.com` (см. «API аукциона»)
- Telegram-уведомления — **grammY**; трафик до `api.telegram.org` идёт через
  общий прокси-стек `shared-proxy` (Xray-core, живёт вне этого репозитория),
  через **http-inbound** (порт 1081) — см. «Прокси»

## Команды


## Архитектура

### Данные (`src/lib/items`)

- `ItemsDatabase` (`index.ts`) — рекурсивно читает все json из `<root>/items`, собирает
  предметы в объект по id (поле `items`). Иконка предмета — `icons/<category>/<id>.png`
  (поле `icon` относительно корня базы, либо `null`).
  Варианты предметов (папки `_variants/<id>`) складываются в поле `variants`;
  чтение вариантов отключается опцией `includeVariants: false` (в приложении
  варианты не читаются).
- `store.ts` — единый экземпляр базы (`itemsDatabase`). База читается один раз,
  **не создавайте новый `ItemsDatabase` на каждый запрос**.
- `catalog.ts` — `toSummary`, `applyFilters` (чистая фильтрация и сортировка),
  `topCategories`, справочники `CATEGORY_TREE`/`RANK_OPTIONS`/`RANK_COLORS`/`SORT_OPTIONS`,
  хелперы `categoryLabel`, `rankLabel`, `rankColor`, `itemName`, `iconUrl`,
  `TOP_CATEGORY_OPTIONS`, `topCategoryValue`, `rankValue` (последние — для команд бота).
  Русские названия категорий лежат здесь — при добавлении категорий правьте `CATEGORY_TREE`.

### API аукциона (`src/lib/auction`)

- `SZApi` — клиент `https://eapi.stalzone.com`. Данные публичные, авторизация
  «по секрету»: заголовки `Client-Id` и `Client-Secret` (<https://eapi.stalzone.com/auth.html>).
  Методы `getLots(item)` и `getHistorySince(item, since, maxPages)` типизированы
  (`AuctionLot`, `PricePoint`); ошибки — исключением.
- `getSzApi()` — берёт креды из `CLIENT_ID` и `CLIENT_SECRET` (для секрета
  поддерживается старое имя `SZ_API_TOKEN`). Нет кредов — `null`, блоки показывают заглушку.
- `getLots` постранично добирает **все** активные лоты (страница 200, ограничение 600).
  `sort`/`order` не используем — сортируем и фильтруем у себя.
- `getHistorySince` — сделки с момента `since` (пачки по 6 страниц): `BACKFILL_PAGES`
  (200) при разовом backfill и `INCREMENT_PAGES` (5) при докачке (докачка идёт каждые
  2 минуты, новых сделок за цикл мало).
- `additional: true` (включён) даёт поля `qlt` (качество), `ptn` (точка), `buyer` и др.
  Для истории доп. поля тянем только с первой страницы: если у предмета нет
  `qlt`/`ptn`, остальные страницы идут без них.

### Кэш данных (`src/lib/auction/data.ts`)

- `loadLots(itemId)` — активные лоты из API, кэш ~1 минуту (`revalidate: 60`), тег `item:<id>`.
- `loadHistory(itemId, days, window)` — история **из PostgreSQL** (страница в API не ходит),
  кэш ~5 минут (`revalidate: 300`). Ключ включает `window` (время, округлённое вниз до 5 минут,
  `windowOf`), поэтому смена фильтров качества/точки мгновенная — фильтрация уже готовых данных.

### Синхронизация истории (`src/lib/sync.ts`)

- `syncItem(itemId, log)` — один предмет: разовый backfill при первом появлении
  (`WORKER_BACKFILL_DAYS`, 30 дней), дальше только новое (с последней сохранённой сделки).
  Если выборка упёрлась в лимит страниц (`complete: false`), `backfilledAt` не ставится
  и `lastSaleTime` не сдвигается — доберём на следующем прогоне (дубликаты отсекает `Sale.key`).
  Ошибки пишутся в `SyncLog` и `ItemSync.lastError` и не останавливают цикл.
- `syncOnDemand(itemId)` — подтягивание по открытию карточки: создаёт строку предмета
  (она нужна как владелец сделок по внешнему ключу), но **избранным не делает**;
  не чаще `SYNC_ON_DEMAND_MIN_MS` (2 минуты), чтобы частые переходы не дёргали API.

### База данных и воркер

- Схема (`prisma/schema.prisma`):
  - `TrackedItem` — предметы, по которым храним историю; поле `favorite` — избранное
    (его синкает воркер и по нему сканируются лоты);
  - `ItemSync` — состояние синхронизации (`backfilledAt`, `lastSyncedAt`, `lastSaleTime`, `lastError`);
  - `Sale` — сделки (время, цена, количество, качество, точка, ключ дедупликации `key`);
  - `SyncLog` — журнал прогонов;
  - `AlertChat` — подписка чата (пороги и фильтры);
  - `AlertEvent` — очередь и лог уведомлений (см. «Алерты по лотам»).
- Миграции — `prisma/migrations/` (сделки и индексы → алерты → фильтры-диапазоны →
  избранное → события по лотам); применяются `bun migrate` или сервисом `migrate`.
- `src/lib/db/sales.ts` — сделки и избранное: `readSales`, `saveSales` (пачками по 1000,
  дубликаты пропускаются), `latestSaleTime`, `saleStats` (средняя без выбросов, медиана,
  число сделок по срезу качества и точки), `lastSalePrice`, `ensureItem`,
  `setFavorite` / `listFavoriteIds` / `isFavorite`.
- `src/lib/db/alerts.ts` — `listActiveAlertChats`, `upsertAlertChat` (настройки),
  `markAlertSent` (постановка в очередь, дедуп по лоту), `listPendingAlertEvents`,
  `markAlertEventSent` (очередь для бота).
- `src/app/actions.ts` — серверный экшен `toggleFavorite`: звёздочка в каталоге
  и на странице предмета переключает избранное.
- `src/worker/index.ts` — воркер с **двумя независимыми циклами**:
  1. **Синк истории** избранных — раз в `WORKER_INTERVAL_MS` (по умолчанию **2 минуты**):
     `syncItem` по каждому избранному. В конце прогона чистит старое (сделки и записи
     `SyncLog` старше `WORKER_RETENTION_DAYS`, 35 дней).
  2. **Скан лотов** — раз в `LOT_SCAN_INTERVAL_MS` (по умолчанию **30 минут**):
     `scanLots` по каждому избранному (см. «Алерты по лотам»).
     Оба цикла идут независимо; SIGTERM/SIGINT — корректное завершение (дожидается
     текущего предмета, закрывает Prisma).
- Отслеживание: избранное задаётся вручную (звёздочка в вебе, `/track` и `/untrack`
  в боте) и само не снимается. Неизбранные предметы фоном не синкаются — их история
  подтягивается только при открытии карточки.
- `src/app/api/health/route.ts` — healthcheck: `SELECT 1` (`await connection()`, чтобы
  роут не закэшировался на сборке).
- Docker: `Dockerfile` — multi-stage с target-ами `web` (standalone) и `worker`
  (фоновые процессы на bun: синхронизация, бот, миграции — один образ с разной командой);
  `docker-compose.yml` — `db`, `migrate` (одноразовый), `web`, `worker`, `bot`
  (подключает внешнюю сеть `shared-proxy-net`).

### Серверное и клиентское

- Нормы обновления аукциона: лоты — раз в минуту, история — раз в 5 минут (это TTL кэша
  в `data.ts`). Документированных лимитов у API нет — наращивать частоту не надо.

- Каталог (`app/page.tsx`) — серверный компонент: собирает краткие версии предметов,
  читает избранное из БД и передаёт всё в клиентский `ItemCatalog`. Раскладка во всю ширину:
  слева меню категорий (`CategoryNav`), сверху поиск, фильтр по рангу и сортировка
  (по рангу / по разделам / А→Я / Я→А; по умолчанию — по рангу). Категории в меню —
  только верхний уровень; показываются те, что есть в данных. Карточки — порциями по 120.
  У каждой карточки звёздочка избранного, **избранные всегда идут первыми**.

- Детальная страница (`app/items/[id]/page.tsx`) — серверный компонент: читает предмет
  по `id` (иначе `notFound()`), читает избранное и показывает иконку, категорию, ранг
  и звёздочку. Характеристик нет — только «История продаж» (`ItemHistory`) и «Текущий
  аукцион» (`ItemLots`), каждый в своём `<Suspense>`. Обращение к `params` обёрнуто
  в `<Suspense>` (требование `cacheComponents`, см. /docs/messages/instant-shell-url-data).

- `ItemHistory` (серверный) при открытии зовёт `syncOnDemand` (троттлинг
  `SYNC_ON_DEMAND_MIN_MS`) и `await connection()`, затем тянет лоты и историю за период;
  дальше работает клиентский `MarketHistory`: фильтры качества (`qlt`) и точки (`ptn`;
  отсутствующая точка считается нулём), график цены (`PriceChart`). Таблица лотов
  («Текущий аукцион», `ItemLots`) живёт в `LotsTable`.

- Статистика рынка: средняя и медиана — по **совершённым сделкам** за выбранный период
  (с учётом фильтров качества/точки). **Средняя считается без выбросов** («вкиды»/переброс
  валюты): отбрасываются верхние `OUTLIER_TRIM` (5%) и цены выше `OUTLIER_MEDIAN_FACTOR` (5×)
  медианы (`cleanedPrices` в `@/lib/auction/market`); сколько отброшено — подписано под
  статистикой. Мин. предложение — минимальный выкуп активных лотов. Прибыль на странице =
  `(1 − MARKET_FEE) × средняя − мин. предложение`, маржа = прибыль / средняя × 100
  (`estimateProfit`).

- Фильтры качества и точки показываются, только если признак есть в данных, но значения
  перечисляются полным диапазоном: заточка 0–15, качество 0–5 (`featureRange`), чтобы
  варианты не «пропадали». Фильтры берутся из адреса (`?days=&qlt=&ptn=`): разбор —
  `parsePeriod`/`parseFeature`, сборка — `marketHref` (`@/lib/auction/period`).

- История агрегируется в `summarize` (`@/lib/auction/market`): ряд графика — ~120 интервалов
  со средней ценой; статистика (средняя, медиана, число сделок и штук, мин/макс, последняя).
  Если лимита страниц не хватило на весь период, UI пишет «период покрыт не полностью».
  Дата/время форматируются детерминированно (`src/lib/format.ts`, Москва UTC+3) — иначе
  SSR и браузер дают разные строки и ломается гидратация.

- Иконки не лежат в `public`, их отдаёт route handler `app/icons/[...path]/route.ts` из базы.

## Алерты по выгодным лотам (снайпинг)

### Идея

Новые «горячие» сделки ловить бессмысленно — их мгновенно скупают боты. Вместо этого
бот периодически перепроверяет **текущий аукцион** по избранным артефактам и присылает
уведомление, если активный лот висит заметно дешевле недавней средней цены **для своего
качества и точки**. То есть алерты идут **только по лотам**; появление новых сделок
уведомлений не вызывает (сделки нужны лишь как база для средней).

### Экономика

- Комиссия площадки `MARKET_FEE` = 5% (`@/lib/auction/market`, общая с сайтом).
- Выбросы: верхние `OUTLIER_TRIM` (5%) и цены выше `OUTLIER_MEDIAN_FACTOR` (5×) медианы.
- Средняя считается по сделкам того же предмета **того же качества и точки** за 7 дней;
  если сделок в срезе меньше `SCAN_MIN_SALES` (по умолчанию 3) — лот пропускаем.

```
прибыль = (1 − 0.05) × средняя − цена выкупа лота
маржа   = прибыль / средняя × 100
```

Порог срабатывания: `прибыль ≥ minProfit` **и** `маржа ≥ minMargin` (если задан), включительно.
Полезная связка: `маржа m%` ⇔ цена лота ниже средней на `5% + m` (например, `margin 10` ⇒
лот минимум на 15% ниже средней).

### Данные

- `TrackedItem.favorite` — избранное: список предметов, которые сканируем (звёздочка в вебе,
  `/track` и `/untrack` в боте). Отдельной таблицы под список скана нет.
- `AlertChat` — подписка чата: `minProfit` (BigInt, по умолчанию 50 000), `minMargin` (Float?),
  `categories` / `ranks` / `qualities` / `points` (наборы; пусто = без ограничения),
  `active`, `title`. Качество — `qlt` 0–5, точка — `ptn` 0–15 (отсутствующая точка = 0,
  отсутствующее качество под непустой набор качеств не подходит).
- `AlertEvent` — очередь и лог отправки: `itemId`, `lotKey`, `quality`, `point`, `lotPrice`,
  `average`, `profit`, `margin`, `lotStart`, `lotEnd`, `lastPrice`, `stats` (JSON — массив
  `{ days, average, median, deals }` за 7/14/30) и `sentAt` (`null` = ещё в очереди).

### Скан (`src/lib/alerts`)

- `profit.ts` — чистая экономика: `ALERT_PERIODS` (7/14/30), `SCAN_MIN_SALES`,
  `estimateFlip(price, average)`, типы `PeriodStats` / `FlipEstimate`.
- `detect.ts` — чистые фильтры и пороги: `matchFilters` (активность, качества, точки, разделы,
  ранги), `matchThreshold` (пороги прибыли/маржи), `detectAlerts(lot, chats, estimate)`.
- `index.ts` — `scanLots(itemId)`:
  1. берём все активные лоты предмета из API (свежие данные каждого цикла), оставляем
     только с выкупом (`buyoutPrice > 0`) — это цена, за которую можно купить сразу;
  2. для каждого лота берём его (качество, точка) из `additional` и считаем среднюю по
     **этому же срезу** за 7 дней (с очисткой выбросов; кэшируем на проход);
  3. `прибыль = 0.95 × средняя − buyout`, `маржа = прибыль / средняя × 100`;
  4. прогоняем фильтры чата (качества/точки/разделы/ранги/пороги) и пишем событие
     в `AlertEvent` с дедупом по `lotKey`.

### Дедуп: одно уведомление на лот

Ключ лота собирается из его полей (`itemId | qlt | ptn | buyout | amount | startTime | endTime`) —
у лота в API нет собственного id. Уникальность `@@unique([alertChatId, lotKey])` + `sentAt`
дают два уровня: повторно по тому же лоту не поставим и не отправим. Если продавец изменит
цену или срок — это будет считаться новым лотом, и уведомление придёт снова.

### Процесс `bot` (`src/bot`)

- `index.ts` — создаёт `Bot`, при старте зовёт `getMe()` (падает сразу, если токен/прокси
  неверные) и `setMyCommands` (палитра команд). Раз в `BOT_POLL_MS` (10 с) забирает
  неотправленные `AlertEvent`, шлёт в чат (с кнопкой избранного) и ставит `sentAt`.
- `commands.ts` — `/start`, `/chatid` (без ограничений) и админские `/menu`, `/status`,
  `/filter`, `/pause`, `/resume`, `/track <id>`, `/untrack <id>`.
  Фильтры: `/filter minprofit 30000`, `/filter margin 10` (`off`), `/filter categories Оружие,Артефакты`,
  `/filter ranks Мастер,Легенда`, `/filter qlt 2-5` (`2,3,4,5`, `все`), `/filter ptn 0-15` (`все`).
- `menu.ts` — настройки кнопками (инлайн-клавиатура): пауза, пресеты прибыли/маржи,
  переключатели качества, точки, разделов и рангов; плюс кнопка «⭐ в избранное» под
  уведомлениями (`favoriteKeyboard`).
- `auth.ts` — `isAllowedUser` по `ALERT_ADMIN_USER_IDS` (**user.id**, не chat.id; пусто =
  менять настройки не может никто).
- `format.ts` — текст уведомления (HTML).
- `proxy.ts` — прокси: **встроенный fetch Bun не умеет socks и не применяет node-агенты**,
  поэтому ходим через нативный `proxy` к http-inbound Xray (1081).

### Уведомление

HTML-разметка; имя предмета ссылкой на `${DOMAIN}/items/<id>`, ранг, цена лота (выкуп),
начало и окончание лота (Москва), последняя сделка по тому же срезу, прибыль (после 5%)
и маржа, качество/точка и рынок тремя строками (7/14/30: средняя · медиана · сделок).

## Прокси `shared-proxy` (вне этого репозитория)

Xray-core с двумя inbound: socks `1080` и http `1081`. Поднимается **отдельным стеком**
(в репозитории его нет, на сервере лежит вне проекта) и создаёт сеть `shared-proxy-net`;
сервис `bot` подключается к ней как к `external` и обращается по **имени контейнера**
`shared-proxy`. Конфиг собирается из переменной `VLESS_URL` при старте контейнера.

Важно: `TELEGRAM_PROXY_URL=http://shared-proxy:1081` — именно **http**, не socks:
встроенный fetch Bun socks не умеет (проверено), а node-агенты он игнорирует. `proxy.ts`
собирает grammY собственный `fetch` с нативным `proxy`.

## Соглашения по коду

- Комментарии — на русском.
- Код простой и читаемый, пригодный для правок руками.
- Условия — в блоках с фигурными скобками, без однострочных `if (...) ...;`.
- Переиспользуемые куски выносим в `src/components` и `src/lib`.
- В `next.config.ts` включены `cacheComponents`, `partialPrefetching`, `reactCompiler`.
  При включённом `cacheComponents` не используются `dynamic`/`revalidate`/`fetchCache`,
  а несрочные данные оборачиваются в `<Suspense>` (см. `node_modules/next/dist/docs/`).
- Бот и воркер разделены по зоне ответственности: воркер не знает про Telegram,
  бот не знает про `eapi.stalzone.com`. Воркер считает лоты и ставит события
  в `AlertEvent`, процесс `bot` их отправляет. Общий код — чтение/запись через Prisma
  и чистые функции (`estimateFlip`, `detect.ts`, `MARKET_FEE`, `OUTLIER_*`).
